DR-DCI(arXiv 표기 “Dr-DCI”): Scaling Direct Corpus Interaction via Dynamic Workspace Expansion. 검색을 에이전트가 직접 호출하는 pull(query, topK) 액션으로 바꾸고, 끌어온 워크스페이스 안에서만 rg·grep·read로 증거를 찾고 검증합니다. 별도 학습 없이 GPT-5.4 nano로 추론만 합니다.

쉽게 말하면

도서관에서 숙제할 때를 떠올려 보세요

질문 하나에 답하려고 1,000만 권짜리 도서관을 뒤져야 한다고 합시다. AI가 자료를 찾는 방식은 크게 세 가지입니다.

① RAG

“사서가 발췌본만 복사해 줌”
  1. 사서에게 질문을 건넨다 (검색)
  2. 사서가 관련 있어 보이는 책 5권의 몇 문단만 복사해 준다
  3. AI는 그 복사본만 보고 답한다
빠르다. 하지만 복사본에 없는 내용은 확인할 방법이 없고, 두 책을 펼쳐 놓고 대조하는 것도 못 한다.

② Raw DCI

“서가 전체를 직접 Ctrl+F”
  1. 사서 없이 AI가 서가에 직접 들어간다
  2. 모든 책에 Ctrl+F(grep)를 돌리고, 필요한 페이지를 직접 펼쳐 읽는다
  3. 여러 책을 가로질러 조건을 조합해 검증한다
정확하다. 하지만 도서관이 커지면 검색 한 번이 끝나지 않는다(시간 초과, 결과 폭주).

③ DR-DCI ← 이 논문

“책을 내 책상으로 가져온 뒤 Ctrl+F”
  1. 사서에게 “관련 있어 보이는 책 500권을 내 책상에 갖다 줘” (pull)
  2. 책상 위 책에서만 Ctrl+F·정독으로 증거를 찾는다 (rg, read)
  3. 새 단서가 생기면 “이것 관련 책 더” → 책상이 넓어진다
사서의 넓은 탐색 + 직접 뒤지는 정밀함. 도서관이 100배 커져도 책상은 ~1,000권 수준으로 유지된다.
RAG와의 결정적 차이
RAG에서는 검색 결과가 곧 답의 재료입니다. DR-DCI에서는 검색 결과가 뒤질 범위(작업 공간)일 뿐이고, 답의 근거는 AI가 그 안에서 직접 찾아 확인합니다. 그래서 저자들은 “검색은 상호작용을 대체하지 말고, 조종해야 한다”고 말합니다.

01 · 문제

스케일과 정밀도의 긴장

RAG는 확장되지만 해상도가 낮고, Raw DCI는 정밀하지만 확장되지 않습니다. 논문은 DCI의 병목을 “로컬 정밀도”가 아니라 코퍼스 수준 탐색을 위한 확장 가능한 메커니즘의 부재로 진단합니다. 그래서 검색에는 확장성을, 셸 상호작용에는 정밀도를 맡깁니다.

RAG / 검색 에이전트

query → retriever
→ top-k 스니펫 → LLM
확장성높음
상호작용 해상도낮음

02 · 선행 연구

DCI 입문: 임베딩 없이, 인덱스 없이, 터미널만으로

DCI(Direct Corpus Interaction)는 같은 그룹의 선행 논문 Beyond Semantic Similarity(arXiv 2605.05242)에서 정식화됐습니다. 정의는 “에이전트가 임베딩 모델, 벡터 인덱스, 검색 API를 우회하고 범용 명령줄 인터페이스로 원시 코퍼스와 상호작용하는 것”입니다.

핵심 개념은 retrieval interface resolution — 문서나 패시지보다 작고 정밀한 단위로 조작할 수 있는 능력입니다. grep 'A' | grep 'B' 한 줄이 “A와 B를 동시에 만족하는 문장”이라는, 임베딩 검색으로는 표현하기 어려운 질의가 됩니다.

  • Claude Sonnet 4.6 백본에서 Qwen3-Embedding-8B 검색 도구를 DCI로 바꾸자 BrowseComp-Plus 69.0% → 80.0%, 비용 $1,440 → $1,016. DCI 논문
  • 최소 하네스 DCI-Agent-Lite(Pi 기반, bash+read, GPT-5.4 nano): 62.9%. 이것이 DR-DCI의 “Raw-DCI” 기준선입니다.
  • 동시기 연구: GrepSeek(arXiv 2605.29307, SFT→GRPO 학습), “Is Grep All You Need?”(arXiv 2605.15184, 하네스 설계가 grep 대 벡터 선택만큼 중요).
workspace — 예시 트레이스

설명용 재구성 트레이스입니다. pull 응답 블록은 논문 부록 A.7 원문이며, rg/read 명령과 출력은 흐름을 보여주기 위한 예시입니다. 실제 셸은 실행되지 않습니다.

03 · 핵심 아이디어

pull = 워크스페이스 확장 액션

숨김 코퍼스 C = {d₁,…,dN}에서 에이전트는 질문별 워크스페이스 Wt ⊆ C를 유지하고, 매 턴 확장(expand) · 조사(investigate) · 종료(finalize) 중 하나를 고릅니다. 아래는 부록의 성공 사례(QID 665) 수치로 재생한 루프입니다.

visible 0 new 0 already visible 0 pull 호출 0

점 하나 ≈ 문서 5개. 회색 = 숨김 코퍼스, 청록 = 워크스페이스에 물질화된 문서, 흰 테두리 = 현재 도구가 건드리는 문서. pull 문서 수는 QID 665 사례 값이며, rg 매치 수·read 구간은 설명용입니다.

    pull 인터페이스

    (ΔWt, Pt, St) = PULL(rt, kt; C, Wt),    Wt+1 = Wt ∪ ΔWt,    ΔWt ∩ Wt = ∅

    하네스가 검색 · 중복 제거 · 물질화(materialize, 워크스페이스에 실제 파일로 배치)를 처리합니다. 반환값은 세 가지입니다.

    • ΔWt: 새로 추가된 문서(이미 보이는 문서는 제외)
    • Pt: 간결한 순위 프리뷰 — “탐색 신호”일 뿐, 답의 근거가 아님
    • St: 워크스페이스 통계(신규 / 기존 / 전체)

    프롬프트는 topK를 300–600 사이에서 고르게 하고, “pull 직후에는 반드시 워크스페이스를 먼저 검색·읽기하고, 진짜 새 단서가 있을 때만 다시 pull하라”고 지시합니다.

    워크스페이스 DCI의 두 패턴

    문서 간(inter-document) DCI

    rg, grep, find, ls로 여러 후보를 가로질러 제약을 조합하고, 브리지 엔티티를 추적하고, 오답 후보를 배제합니다. 이걸 막으면 정확도가 82→40으로 반토막 납니다(→ 어블레이션).

    문서 내(intra-document) DCI

    read에 줄 오프셋이나 문자 윈도우를 주어 정확한 증거 구간을 찾습니다. 출력이 잘리면 하네스가 offset/charOffset 이어읽기 힌트를 줍니다.

    04 · 아키텍처

    터미널 친화 워크스페이스

    성능의 상당 부분은 모델이 아니라 인터페이스 엔지니어링에서 나옵니다. 노드를 눌러 각 계층의 설계 디테일을 보세요. Appendix A.8

    의사코드: pull()

    # 의사코드 — 논문 설명을 바탕으로 한 개념 구현이며 저장소의 실제 코드가 아님
def pull(query: str, top_k: int, ws: Workspace) -> str:
    assert 300 <= top_k <= 600                      # 프롬프트 권장 범위
    hits = retriever.search(query, k=top_k)         # dense(Qwen3-Emb-8B) 또는 BM25, :8002/retrieve
    new  = [h for h in hits if h.doc_id not in ws.ids]   # ΔW ∩ W = ∅  (중복 제거)
    for h in new:
        name = shell_safe(h.title)                  # 셸 안전 파일명, 원제목/URL/순위/출처는 메타데이터로
        os.link(store.path(h.doc_id), ws.root / name)    # 하드링크 물질화, root-flat(폴더 없음)
        if is_single_line(ws.root / name):
            reflow(ws.root / name, width=1200)      # OCR/PDF 한 줄 문서 리플로
        ws.add(h.doc_id, meta=h.meta)
    return render_preview(                          # P_t, S_t — 순위는 경로가 아니라 응답으로 전달
        new=len(new), dup=len(hits) - len(new), total=len(ws),
        top=[n.name for n in new[:20]],
        hint="search/read the visible workspace before pulling again")

    10 · 관련 연구

    에이전트 검색 인터페이스 설계 지도

    DR-DCI는 유일한 혁신이 아니라 같은 아이디어 축 위의 한 지점입니다. 후속 RARG 논문은 “Pi-Serini, RISE, and DR-DCI … use sparse or dense retrieval to construct or expand a bounded candidate space”라고 정리합니다.

    12 · 한계와 열린 질문

    한계, 향후 연구, 인용

    한계

    • 리콜 성공 ≠ 판별 성공. QID 221: 정답 문서가 워크스페이스에 들어왔지만 에이전트는 같은 저자의 다른 책을 골랐습니다. A.11.3
    • 비교 공정성. Wiki-18 기준선은 모델 크기·학습법·환경이 달라 통제 비교가 아닙니다.
    • 표본 크기. Wiki-18 분할당 50문항, 스케일링 100문항.
    • 외삽. Raw-DCI 800K 초과 구간(논문 그림 3)은 실측이 아닙니다.
    • 방해 문서. 무작위 FineWeb은 어려운 오답보다 쉬울 수 있습니다.
    • 랭킹 과제. BRIGHT/BEIR NDCG@10 평균 54.2로 ReasonRank-32B(47.0)보다 높지만 DCI-Agent-Lite(56.7)보다 낮습니다. A.3
    • 상한. 리트리버 품질(Dense > BM25)과 LLM의 셸 조작 능력에 묶입니다.
    • 단일 백본·자체 평가. 모든 수치는 GPT-5.4 nano, 저자 자체 평가이며 독립 재현은 찾지 못했습니다.
