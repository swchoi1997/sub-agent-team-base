팀원마다 다른 AI를 쓰면,
품질은 어떻게 맞출까?

한 프로젝트에서 누구는 Claude Code를, 누구는 Codex나 Cursor를 씁니다. 결과물 품질이 들쭉날쭉해지지 않을까요? 전 세계 회사와 오픈소스 프로젝트가 찾은 답을 비유와 예시로 아주 쉽게 풀어봤습니다.

"모두 같은 도구를 쓰게 하라"가 아닙니다.
"누가 무엇으로 만들었든, 같은 검사를 통과하게 하라"입니다. 지침은 한 곳에 모으고(AGENTS.md), 품질은 자동 검사(CI)와 사람 리뷰로 지킵니다.

읽는 시간 약 10분 · 처음부터 차례로 읽으면 가장 이해가 쉬워요.

먼저 비유로 이해하기

식당 주방을 떠올려 보세요

요리사가 다섯 명 있는 식당이 있어요. 각자 손에 익은 칼과 프라이팬이 다릅니다. 어떤 요리사는 독일제 칼을, 어떤 요리사는 일본제 칼을 써요. 그런데 손님 입장에선 누가 만들든 같은 맛이 나와야 하죠.

이 식당은 모든 요리사에게 같은 칼을 쓰라고 강요하지 않아요. 대신 이 세 가지를 합니다.

📖같은 레시피북모두가 같은 레시피를 봐요= AGENTS.md
→
🌡️출고 전 검사온도·간·양을 기계로 재요= CI 자동 검사
→
👨‍🍳주방장 시식마지막엔 사람이 맛봐요= 사람 코드 리뷰

소프트웨어로 바꾸면 이렇습니다. 요리사 = 개발자, 칼 = AI 에이전트(Claude Code, Codex, Cursor 등), 요리 = 코드 변경(PR). 이 문서 전체가 이 세 칸을 어떻게 잘 만드는지에 대한 이야기예요.

칼(도구)을 통일하는 것보다, 레시피와 검사와 시식을 통일하는 게 훨씬 효과적이다.

AI 에이전트 코드 짜는 AI 조수

명령을 받으면 스스로 파일을 읽고, 코드를 고치고, 테스트까지 돌리는 AI예요. Claude Code, Codex, Cursor, Copilot, Gemini CLI 등이 있어요.

하네스 AI를 감싼 실행 틀

같은 AI 모델이라도 어떤 프로그램(도구) 안에서 돌리느냐에 따라 행동이 달라져요. 그 "프로그램"을 하네스라고 불러요. 말의 마구(harness)처럼 AI를 붙잡고 방향을 잡아주는 틀이에요.

PR (Pull Request) "제 변경을 합쳐 주세요" 요청

코드를 고친 뒤, 본 코드에 합치기 전에 다른 사람에게 검토를 요청하는 단위예요. "머지(병합)"는 그 요청이 받아들여져 합쳐지는 것이에요.

CI 자동 검사 로봇

PR이 올라올 때마다 자동으로 테스트·린트·보안 검사를 돌리는 시스템이에요. GitHub Actions가 대표적이에요. 사람·AI 구분 없이 똑같이 검사해요.

린터 / 포매터 맞춤법 검사기

린터는 코드의 실수나 나쁜 습관을 찾아주고, 포매터는 들여쓰기·줄바꿈 같은 모양을 통일해요. 글쓰기의 맞춤법 검사기와 비슷해요.

AGENTS.md AI용 업무 안내서

저장소 루트에 두는 마크다운 파일로, "이 프로젝트에선 이렇게 일해"라고 AI에게 알려줘요. 여러 AI 도구가 공통으로 읽는 표준이 됐어요.

CLAUDE.md Claude Code 전용 안내서

Claude Code가 기본으로 읽는 파일이에요. 안에 @AGENTS.md 한 줄을 넣으면 AGENTS.md 내용을 불러와 써요.

Agent Skills 재사용 업무 매뉴얼

SKILL.md 파일로 "DB 마이그레이션 추가하는 법" 같은 반복 절차를 적어 두면, 필요할 때 AI가 꺼내 써요. 2025년 12월 개방형 표준이 됐어요.

MCP AI용 공용 콘센트

AI가 이슈 트래커, 사내 문서, DB 같은 외부 도구에 연결하는 표준 규격이에요. 어떤 AI든 같은 MCP 서버에 꽂으면 같은 정보와 도구를 써요.

훅 (Hook) 도구 안의 자동 경보기

AI가 파일을 고치기 직전·직후에 자동으로 실행되는 스크립트예요. 위험한 작업을 막을 수 있지만, 그 도구를 쓰는 사람에게만 적용돼요.

브랜치 보호 합치기 전 필수 조건

"검사 전부 통과 + 사람 승인 1명 이상"이 아니면 본 코드에 합칠 수 없게 GitHub에서 잠가 두는 설정이에요.

CODEOWNERS 구역별 담당자

"결제 코드는 김 팀장이 꼭 봐야 한다"처럼 폴더마다 필수 리뷰어를 지정하는 파일이에요.

TL;DR

핵심은 딱 3가지

1

지침은 하나로

도구마다 안내서를 따로 쓰면 조금씩 내용이 어긋나요. AGENTS.md 하나를 원본으로 두고, 나머지 도구는 그걸 가리키게 해요.

2

품질은 검사로

안내서는 AI가 "참고"만 해요. 꼭 지켜야 할 규칙은 자동 검사(CI)로 막아요. 표준 관리 단체조차 "파일은 안내하고, 검사가 결정한다"고 말해요.

3

마지막은 사람

AI 덕에 PR은 2배 늘었지만 리뷰 시간도 거의 2배가 됐어요. 작은 PR, AI 사용 공개, "사람이 모든 줄을 이해하고 책임진다"가 공통 원칙이에요.

모든 AI에게 공통된 약점

더 중요한 건, 어떤 AI든 똑같이 가진 약점이 있다는 점이에요.

🧪 Sonar 연구 (Java 과제 4,400개 이상)

모델마다 "성격"은 달랐어요(장황함, 복잡도, 주석 습관). 그런데 모든 모델이 심각한 취약점을 만들었고, 문제의 90% 이상이 코드 스멜(나쁜 냄새가 나는 코드)이었어요. "가장 안전한 모델은 없다"는 결론이에요.

📉 GitClear 분석 (2억~6억 줄)

AI 시대에 복사·붙여넣기는 늘고(8.3% → 12.3%), 기존 코드를 정리하는 리팩터링은 크게 줄었어요. 새 코드가 기존 코드와 연결되는 정도도 2023년 대비 35% 떨어졌어요.

💡 예시로 생각해 보기 팀 전원을 Claude Code로 통일했다고 해 봐요. 도구 간 차이는 사라지지만, "비슷한 함수를 또 만드는 습관"은 그대로 남아요. 반면 "중복 코드가 5% 넘으면 PR 실패" 검사를 CI에 넣으면, 어떤 AI가 만들었든 걸러져요.
도구 통일로는 공통 약점을 못 고친다. "검증 통일"이 편차와 공통 약점을 한 번에 줄인다.

# AGENTS.md  (ERP 백엔드 예시)

## Setup & commands
- Package manager: pnpm (npm/yarn 사용 금지)
- 모든 소스 변경 후 반드시 `pnpm lint && pnpm typecheck && pnpm test`

## Boundaries
- 수정 금지: `dist/`, `generated/`, `db/migrations/`의 기존 파일
- 요청된 작업 범위만 변경. 무관한 리팩터링·포맷 변경 금지

## Architecture rules
- 레이어 방향: api → application → domain
- 금액 계산은 `domain/money`의 Money 타입만 (부동소수점 금지)
- 회계 전표 변경 전 `docs/adr/0007-ledger.md` 먼저 읽기

## Testing
- 버그 수정은 실패하는 테스트를 먼저 추가
- 기존 유틸 재사용(중복 구현 금지) — `src/shared/` 먼저 검색

## PR
- 커밋 트레일러: `Assisted-by: <agent>:<model>`
- PR 하나 = 논리적 변경 하나, 비테스트 코드 400줄 이하

✔ 명령어가 구체적 · ✔ 금지 경로가 명확 · ✔ 긴 설명 대신 "필요하면 이 문서를 읽어라"는 포인터만 · ✔ 50~150줄 정도

질문 3 · 가장 중요

도구와 상관없이 품질을 강제하는 법

원칙: 입력(지침)을 통일하려 애쓰지 말고, 출력(결과 코드)을 같은 기준으로 판정하라.

🛣️ 고속도로 비유: 훅 vs CI 훅은 내 차에 달린 차선이탈 경고예요. 빠르게 알려주지만, 내 차(그 도구, 그 세션)에만 달려 있어요.
CI는 모든 차가 지나가야 하는 톨게이트 검문소예요. 어떤 차를 타고 왔든 똑같이 검사해요.
→ 팀원마다 다른 도구를 쓴다면, 훅은 "빠른 피드백"용이고 최종 판정은 반드시 CI에서 해요.

🎮 직접 해 보기: PR 검문소 시뮬레이터

서로 다른 AI 에이전트가 만든 PR을 하나 고르고 "검사 시작"을 눌러 보세요. 같은 관문을 차례로 통과하는 모습을 볼 수 있어요.

    예시 PR은 이해를 돕기 위해 만든 가상의 상황이에요. 어떤 에이전트가 이런 실수를 더 잘한다는 뜻이 아니에요.

    5초 미만

    Stripe의 AI는 사람 엔지니어와 같은 린터, 같은 규칙 파일, 같은 CI를 거쳐요. 개발자들은 여전히 Claude, Cursor 등 각자 도구로 일해요. 즉 Stripe도 도구를 통일하지 않고 관문을 통일했어요.

    📄 CI 설정 예시 보기 (GitHub Actions) 
    name: ci
on: [pull_request]
jobs:
  gate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pnpm install --frozen-lockfile
      - name: Agent rule files in sync   # 지침 사본이 원본과 같은지
        run: |
          npx rulesync generate
          git diff --exit-code -- AGENTS.md CLAUDE.md .cursor/rules
      - run: pnpm lint && pnpm typecheck          # 린트 + 타입
      - run: pnpm test -- --coverage             # 테스트 + 커버리지
      - name: Architecture rules
        run: npx depcruise src --config .dependency-cruiser.cjs
      - name: Secrets & SAST
        run: |
          gitleaks detect --no-banner
          semgrep ci
      - name: PR size guard                  # 400줄 넘으면 실패
        run: |
          CHANGED=$(git diff --numstat origin/${{ github.base_ref }}... -- ':!**/*.test.*' | awk '{s+=$1} END {print s}')
          if [ "$CHANGED" -gt 400 ]; then echo "PR too large. Split it."; exit 1; fi

    출처: Faros AI "The AI Productivity Paradox"(1,255개 팀), Sonar 2026 State of Code(1,100명 이상). 두 회사 모두 분석 도구 판매사라 방향성 지표로 읽어 주세요.

    📦 택배 비유 물류센터에 택배가 2배로 들어오는데, 검수 직원은 그대로예요. 상자는 2.5배로 커졌고요. "다 믿진 않지만 다 열어보지도 못하는" 상태 — Sonar는 이걸 "검증 부채(verification debt)"라고 불러요.

    그래서 다들 이렇게 해요

    ✂️ PR을 작게

    비테스트 코드 400줄 넘으면 나누게 해요. 작은 상자가 검수하기 쉬워요.

    🏷️ AI 사용 공개

    커밋에 Assisted-by: claude-code:모델명 같은 표시를 남겨요. 리뷰어가 어디를 더 볼지 알 수 있어요.

    ✍️ 사람이 서명

    "제출자가 모든 줄을 읽고 이해했다"가 원칙이에요. AI는 책임자가 될 수 없어요.

    AI 리뷰 봇은 "1차 필터"까지만

    GitHub Copilot 코드 리뷰는 누적 6,000만 건을 넘었고, 리뷰의 71%가 실행 가능한 피드백을 남겼어요. 쓸모가 있어요. 하지만 병합 승인은 사람이 해요. LLVM은 사람 검토 없이 코멘트를 올리는 자동 리뷰 도구를 금지했고, Django는 남의 PR에 AI 리뷰를 함부로 돌리지 말라고 요청해요.

    AI가 코드 작성→ 작성자가 전부 읽고 이해→ CI 자동 검사→ AI 리뷰 봇 (1차)→ 사람 리뷰어 승인→ 병합
    AI는 코드를 빨리 만들지만, 책임은 사람에게 있다. 리뷰하기 쉽게 작게 쪼개는 것이 핵심이다.

    📐 스펙 주도 개발 (SDD)

    🏗️ 건축 설계도 비유 인부(AI)마다 망치질 스타일이 달라도, 같은 설계도로 짓고 같은 준공 검사를 받으면 같은 건물이 나와요. 여기서 설계도는 "사람이 읽는 문서"가 아니라 실행되는 명세예요: 계약 테스트, OpenAPI, BDD 시나리오.
    💡 예시: 주문 API 먼저 "POST /orders는 재고가 없으면 409를 돌려준다"는 계약 테스트를 merge해요. 그다음 Claude Code든 Codex든 구현 PR을 올리면, 해석이 달라도 같은 계약 테스트로 판정돼요. 큰 결정은 AGENTS.md에 다 적지 말고 "docs/adr/를 참조하라"는 포인터만 둬요.

    병렬 작업 원칙: 에이전트 하나 = 브랜치 하나 = 격리된 작업 공간(git worktree) 하나 = 작은 PR 하나. 합치는 건 CI 머지 큐에서만.
